# Especificação — Prompt de Curadoria de Vagas (CalibraCV)
## Documento de revisão externa — eficiência + efetividade (v3.0)

---

## 1. Objetivo deste documento

Este documento submete a revisores externos (modelos de IA atuando como pares críticos) o **prompt de curadoria de vagas** do CalibraCV, com dois objetivos simultâneos e de igual peso:

- **Efetividade** — máxima qualidade de classificação (skills, senioridade, cargo canônico).
- **Eficiência** — menor custo de operação possível, sem sacrificar a efetividade.

Não buscamos "mais qualidade a qualquer custo" nem "mais barato a qualquer custo". Buscamos o ponto ótimo entre os dois.

Anexamos **duas versões** do prompt:
- **Anexo A — V7 (em produção):** o prompt atual, validado em produção.
- **Anexo B — Nova V8.2 (proposta):** uma evolução da V7 que reduz o tamanho (higiene de forma, sem perda comportamental) e incorpora um conjunto de correções de efetividade derivadas da rodada anterior de revisão externa.

Pedimos que os revisores avaliem ambas e apontem (a) melhorias de efetividade e (b) reduções de custo adicionais que ainda preservem a qualidade.

---

## 2. Contexto do produto e do pipeline

O CalibraCV analisa perfis profissionais contra dados reais do mercado de trabalho brasileiro. O prompt aqui revisado roda no **pipeline de curadoria de vagas**: recebe vagas brutas (título + descrição + senioridade da fonte) e devolve um JSON estruturado por vaga, contendo:

1. **skills** — competências técnicas e comportamentais, classificadas por tipo (technical/behavioral/hybrid) e, quando comportamentais/híbridas, por grupo pedagógico (1 de 9 grupos).
2. **seniority_inferred** — nível hierárquico (Estágio, Aprendiz, Trainee, Júnior, Pleno, Sênior, Especialista, Gestão, Indefinido), com regras anti-invenção rigorosas.
3. **canonical_role** — cargo canônico reconhecível no mercado BR, via algoritmo de 6 etapas + regras de normalização e desambiguação + uma Lista de Referência.
4. **work_model** — REMOTO / HÍBRIDO / PRESENCIAL.
5. **canonical_confidence** — confiança na atribuição do cargo canônico.
6. **description_curated** — trechos originais de requisitos/responsabilidades.
7. **proposed_taxonomy_mapping** e **proposed_alias** — propostas de novos mapeamentos de cargo/skill para a taxonomia, cada uma com um campo `confidence` que alimenta um gate de auto-promoção.

**Modelo de execução:** o prompt roda no **Claude Haiku 4.5** (promovido a primário após teste A/B contra Sonnet: venceu em qualidade sob arbitragem e é substancialmente mais barato). O prompt é estático e usa prompt caching (cache_control) — é enviado a cada chamada, mas com custo de cache_read após a primeira escrita.

**Volume de referência para projeções:** ~5.000 vagas/dia, processadas em janelas de 100 vagas (3 chamadas de ~34/33/33 vagas), ~50 janelas/dia.

---

## 3. O que muda da V7 (Anexo A) para a Nova V8.2 (Anexo B)

A Nova V8.2 evolui a V7 em dois eixos: **higiene de forma/redundância** (sem alterar comportamento) e **correções de efetividade** (ajustes pontuais de regra derivados da rodada anterior de revisão externa). As mudanças de forma, verificadas item a item:

| Mudança | Tipo | Conteúdo afetado |
|---|---|---|
| Boxes ASCII (┌─│└) do algoritmo de canonical_role → texto corrido | Forma pura | As 6 Etapas continuam idênticas em conteúdo |
| Remoção de comentários meta ("regra reescrita V7", "regras mantidas de V6") | Lixo (não instrui o modelo) | Nenhum |
| Consolidação das faixas de confidence duplicadas entre `proposed_taxonomy_mapping` e `proposed_alias` (eram idênticas) | Redundância literal | As faixas e a calibração específica de cada campo permanecem |
| Corte de 1 das 3 repetições do critério "criou novo → emite / usou existente → omite" | Redundância | Critério dito uma vez de forma clara |
| Exemplo JSON de `proposed_taxonomy_mapping` enxuto (removidos campos irrelevantes ao ponto) | Forma | O par source_term↔target_canonical_label↔confidence permanece |
| Fusão de 2 linhas que mapeavam RPA → "Desenvolvedor de Automação" | Redundância | Mapeamento idêntico |

**Resultado das mudanças de forma:** ~14.155 tokens de input vs ~14.700 (V7) — redução de ~545. As correções de efetividade somam ~+403 tokens de input (cacheável), mantendo a Nova V8.2 (~14552 tok) abaixo da V7.

**Otimização de OUTPUT adicional (a maior economia real):** a Nova V8.2 instrui o modelo a **omitir** o campo `behavioral_group` em skills do tipo `technical`, em vez de emitir `"behavioral_group": null`. Isso foi validado contra o parser de produção (`normalize-result.ts`), que para skills technical **força o valor `null` ignorando o que o LLM emite** — ou seja, o `null` emitido hoje é puro desperdício de tokens de saída. O campo permanece obrigatório para skills `behavioral`/`hybrid`. Economia estimada: **~$415/ano**, sem qualquer perda de qualidade (campo ausente é semanticamente idêntico a `null`) e sem alteração de contrato (o parser já trata a ausência).

**Correções de efetividade incorporadas nesta versão** (derivadas da rodada anterior de revisão externa; alteram comportamento de forma pontual e foram validadas contra o histórico de decisões do projeto e o estado real do banco):
- **Senioridade — gate anti-invenção + régua de anos reconciliada:** o gate bloqueia inferência por *sinais fracos* (graduação, anos-piso baixos, stack, nome do cargo) e **preserva** a inferência por *escopo forte* (Fonte 3) e *anos que discriminam* (Fonte 4: 5+ → Sênior; 2–5 → Pleno só com escopo; teto baixo → Júnior). A Fonte 4, o gate e a definição de "Pleno" em NÍVEIS VÁLIDOS ficam coerentes entre si; mantém a trava anti-fallback de "Pleno". Distinção operacional: piso mínimo baixo ("1+ ano") → Indefinido; teto baixo ("até 2 anos") → Júnior.
- **"Coordinator"/"Coordenador" → Gestão:** unificado na precedência absoluta; removida a exceção que tratava "Coordinator" como contribuidor individual ("Pleno").
- **Consistência dos exemplos de referência:** todos passam a emitir `seniority_confidence`; as skills `hybrid` trazem `behavioral_group`; os `proposed_taxonomy_mapping` aparecem **dentro do JSON** dos exemplos (não mais em nota textual) e trazem `confidence` — alinhando os few-shots ao formato que o prompt exige.
- **Formato de entrada:** uniformizado para o formato real `<job><![CDATA[...]]></job>` nos exemplos **e na seção FORMATO DE ENTRADA** (eliminado o array JSON vestigial da migração).
- **Skills em lowercase:** corrigido o único exemplo de `proposed_alias` cujo `name` estava capitalizado.
- **Catálogo:** "Data Scientist" e "Customer Success Manager" passam a traduzir ("Cientista de Dados", "Gerente de Customer Success"); "Gerente de TI" e "Analista de Infraestrutura de TI" entram na Lista de Referência.
- **Número dos qualificadores:** a Lista de Referência passa a ser a autoridade de singular/plural (substitui a regra cega de "sempre plural"); fora da Lista, usa-se a forma predominante no mercado.
- **`source_term` sem senioridade:** o `proposed_taxonomy_mapping.source_term` remove o qualificador de nível já capturado em `seniority_inferred`, mantendo só o cargo funcional — evita aliases redundantes por senioridade no catálogo.
- **Higiene de clareza:** regra das 20 skills reformulada para seleção *antes* de emitir (evita truncamento autoregressivo); notação das faixas de confidence uniformizada; exemplo da categoria `translation` trocado por um par sem ambiguidade.

**Itens deliberadamente NÃO compactados** (preservação de efetividade — registramos como candidatos para os revisores avaliarem):
- As listas de exclusão de termos genéricos no CAMPO 1 (EXCLUSÕES vs termos guarda-chuva) — têm sobreposição parcial mas propósitos sutilmente distintos; fundir arriscaria ambiguidade.
- Os 2 exemplos de referência adicionais (Analista de Segurança, Analista de Gestão de Projetos) — cada exemplo é um few-shot que ancora desambiguação não-trivial.
- As ~13 regras absolutas e as ~238 regras de mapeamento (→) das seções de normalização/desambiguação — conteúdo comportamental de alto valor.

## 4. Projeções de custo (honestas, com premissas explícitas)

Apresentamos os custos que conseguimos calcular com confiança, separando o que muda do que não muda. Preferimos números relativos (delta entre versões) a absolutos, porque o custo total depende de premissas de preço/volume que variam.

**Premissas:** Haiku 4.5; cache_write $1,25/M, cache_read $0,10/M, output $5,00/M tokens; janela de 100 vagas em 3 chamadas (1 cache_write + 2 cache_read); 50 janelas/dia; 1,825M vagas/ano.

### 4.1. Custo do system prompt (input, cacheável)
- V7 (~14.700 tok): **~$389/ano**
- Nova V8.2 (~14552 tok, já com as correções de efetividade): **~$385/ano**
- Economia da otimização Tier 1-3: **~$14/ano**

A economia de input é modesta porque o cache_read é barato ($0,10/M). O valor da Nova V8.2 está mais na **higiene e legibilidade** do que na economia direta.

### 4.2. Custo de output e otimizações
O eixo de output tem mais margem de economia que o input. Mapeamos:

- **Campo `confidence`** (em `proposed_alias`/`proposed_taxonomy_mapping`, ~2,8 emissões/vaga, ~7 tok cada): **~$179/ano**.
- **Omitir `behavioral_group: null`** em skills technical (aplicado na Nova V8.2): **~$415/ano economizados**, sem perda de qualidade. É a maior alavanca de output identificada e foi validada contra o parser.

**Decisão sobre `confidence` numérico vs enum:** consideramos trocar o número (`0.92`) por um enum de 3 níveis. A economia seria de apenas **~$64-89/ano** (a maior parte do custo da emissão é a chave repetida, não o valor decimal). **Mantivemos o número** — o ganho é desprezível e o número preserva uma vantagem operacional: recalibrar um limiar (`0.85 → 0.88`) é mudança de configuração em banco, sem reescrever o prompt; com enum, os limiares ficariam fixados no que o modelo emite.

**Decisão sobre encurtar chaves de output:** rejeitada. Nomes descritivos (`confidence`, `seniority_confidence`, `canonical_confidence`) servem de sinal semântico que o modelo usa para preencher corretamente, e são consumidos pelo código. Encurtá-los economizaria ~$153/ano contra risco real à qualidade (perda de sinal no Haiku) e quebra de contrato. Para output, a alavanca certa é *omitir campos sem informação* (como o `behavioral_group: null`), não renomear.

**Pergunta em aberto de maior potencial (para os revisores e auditoria de código):** o campo `confidence` por skill é emitido ~10×/vaga (~$500/ano) e o parser o extrai com default 0.50. **Se ele não for consumido por nenhuma decisão downstream** (persistência, gate de skills, ranking), removê-lo seria a maior economia de output disponível — maior que o `behavioral_group`. Ao contrário do `behavioral_group`, isto não pôde ser confirmado pelo código disponível e exige verificação do uso real antes de qualquer mudança.

### 4.3. Custo dominante (não afetado por edição de prompt)
O grosso do custo de produção está no **processamento das vagas em si**: o input das descrições (não-cacheável, varia por vaga) e o output da classificação completa por vaga. Esse custo é intrínseco à tarefa e **não muda** com otimização do prompt. Tanto a otimização de input (~$14/ano) quanto a do campo confidence (~$89/ano) são marginais frente a ele.

**Implicação para os revisores:** otimizações de tamanho do prompt têm impacto pequeno no custo. Se o objetivo for redução de custo significativa, as alavancas reais estão fora do texto do prompt (ex: modelo, volume de vagas processadas, política de cache, filtragem de vagas antes da curadoria) — fora do escopo desta revisão. Dentro deste documento, o foco mais produtivo é **efetividade** (qualidade de classificação) com o tamanho já enxuto da Nova V8.2.

## 5. Perguntas aos revisores

Pedimos foco crítico nos seguintes pontos, em ordem de prioridade:

**Efetividade (prioritário):**
1. Há **regras ambíguas, conflitantes ou que se sobreponham** de forma que possa gerar classificação inconsistente? (especialmente entre as Etapas de canonical_role, as regras de desambiguação e as regras A-E de hierarquia bilíngue)
2. Há **lacunas de cobertura** — tipos de vaga, cargos ou padrões de título/descrição comuns no mercado BR que o prompt não trata bem?
3. As **regras de senioridade** (precedência de título, gate de consistência, anti-invenção, fontes 1-5) cobrem bem os casos reais? Há risco de "Indefinido" excessivo ou de inferência indevida?
4. A classificação de **skills** (technical/behavioral/hybrid + 9 grupos comportamentais) está bem especificada? Os exemplos few-shot são suficientes e representativos?
5. O **gate de confidence** (faixas ≥0.85 / 0.70-0.85 / <0.70 para auto-promoção de aliases/mappings) está bem calibrado conceitualmente?

**Eficiência (secundário, sem sacrificar o acima):**
6. Há **redundância adicional** removível sem perda de comportamento, além das já aplicadas na Nova V8.2? (vejam os "itens deliberadamente não compactados" na seção 3 — concordam em mantê-los, ou veem como cortar com segurança?)
7. Alguma seção poderia ser **reescrita de forma mais densa** preservando todas as regras?
8. **Output:** além da omissão do `behavioral_group: null` (já aplicada), veem algum outro campo emitido que carregue valor determinístico/redundante e possa ser omitido sem perda? Nossa análise indicou que `behavioral_group` é o único caso desse tipo — concordam, ou identificam outro?

**Observações para a auditoria de código (não bloqueiam esta revisão; validadas por grep amplo nos callers + histórico do projeto):**
Três campos lidos pelo parser (`confidence` top-level, `reasoning`, `secondary_role`) são **vestígios da arquitetura anterior de curadoria** — um pipeline com extrator Sonnet e uma etapa de detecção de multi-papel no código (pré-LLM), cujo output era mais rico (incluía `canonical_role_confidence`, `canonical_role_reasoning` e o papel secundário). A simplificação para o pipeline atual (prompt único estático + Haiku) eliminou as fontes dos três; **hoje o prompt não emite nenhum deles**. Status: **os três já foram removidos** do parser, dos callsites e do schema num cleanup de código separado — não impactou o comportamento do prompt nem esta revisão. Registro do que eram:
- `confidence` top-level: lido pelo parser, nunca emitido, nunca consumido — órfão puro.
- `reasoning`: lido pelo parser e nunca consumido; tem um "irmão" que grava `null` em `function_orchestrator_role_items` (limpar ambos no mesmo PR).
- `secondary_role`: nasceu como metadado auxiliar de vagas multi-papel — por design original nunca foi canônico, nunca participou de auto-promoção e nunca foi exibido ao usuário. Sua fonte (a etapa pré-LLM de multi-papel) foi removida na simplificação; hoje só a Camada 0 (cache) reaproveitava valores fósseis, criando uma assimetria sem propriedade de negócio. Sem consumo de produto e sem caso de uso no roadmap → removido.

**Correção de consistência aplicada na Nova V8.2 (efetividade):** os dois exemplos JSON do prompt divergiam — o de abertura emitia `seniority_confidence`, o do FORMATO DE SAÍDA o omitia. Como o modelo tende a imitar o exemplo final, isso induzia omissões ocasionais de `seniority_confidence`; e uma omissão faz o roteamento forçar `seniority_inferred = "Indefinido"` (via guardrail defensivo), inflando falsamente esse bucket. A Nova V8.2 alinha todos os exemplos do prompt — emissão de `seniority_confidence`, `behavioral_group` e `confidence` consistente em cada um (correção já aplicada). A instrumentação da taxa de omissão (espelhando o contador que já existe para `canonical_confidence`) fica para uma sprint posterior — é a única medição que valeria fazer cedo, mas não bloqueia.

**Formato de resposta solicitado a cada revisor:** para cada ponto, indicar se é melhoria de efetividade ou de eficiência, a localização exata no prompt, o problema, e a correção sugerida — distinguindo claramente o que preserva comportamento do que o altera.

Extraia todas as competências mencionadas — técnicas (hard skills) e comportamentais (soft skills).
A ordem de aparecimento considera primeiro o title e depois o description.
A deduplicação ocorre após a normalização.
RESPONSABILIDADES vs. COMPETÊNCIAS: extraia apenas competências que o candidato deve POSSUIR.
Atividades listadas como obrigações do cargo (ex: "conduzir reuniões", "elaborar relatórios")
não são skills, a menos que sejam competências reconhecidas no mercado
(ex: "gestao de pessoas", "lideranca de equipes", "comunicacao").

FORMATO:
- Skills técnicas: manter na forma canônica de mercado (geralmente inglês), lowercase, sem acentos
  (ex: "kubernetes", "react", "sql", "python", "docker")
- Skills comportamentais/soft: em português, lowercase, sem acentos
  (ex: "gestao de pessoas", "lideranca", "comunicacao")
- Mínimo 2 caracteres, máximo 50 por item (exceção: linguagens de programação consolidadas
  de 1 caractere são permitidas, ex: "r", "c")
  Termos de 2 caracteres consolidados são válidos (ex: "go", "c#", "f#", "qa", "ui", "ux", "bi", "ia")
- Sem duplicatas
- Ordem de aparecimento no texto original
- Máximo 20 itens; se exceder, remova soft skills começando da última menção no texto
  em direção à primeira, até atingir 20 itens.
  Se ainda exceder 20 após remover todas as soft skills, mantenha apenas as 20 primeiras
  hard skills por ordem de aparecimento no texto.

NORMALIZAÇÃO:
- Abreviações óbvias: "JS" → "javascript", "k8s" → "kubernetes"
- Variações de grafia: normalize para a forma mais comum ("react.js" → "react")
- Ferramentas distintas são skills distintas: "AWS S3" e "AWS Lambda" são itens separados

EXCLUSÕES — remova termos que são contexto, não competências, quando aparecerem ISOLADAMENTE
(não como parte de uma skill composta como "engenharia de software" ou "seguranca de sistemas"):
tecnologia, sistemas, informatica, computador, internet, ferramentas, software, hardware, automacao, banco de dados

PROIBIDO INFERIR SKILLS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Esta regra tem precedência sobre cobertura. Falhar em mencionar uma skill é preferível a inventar uma.

Extraia APENAS competências que aparecem TEXTUALMENTE no title ou na description, ou são abreviação direta documentada (ex: "JS" → "javascript", "k8s" → "kubernetes", "RN" → "react native", "TS" → "typescript").

NUNCA infira:
* A partir do canonical_role (ex: NÃO incluir "SQL" só porque o canonical é "Analista de Dados")
* A partir da área da vaga (ex: NÃO incluir "machine learning" em vaga de consultor de energia sem menção explícita)
* A partir da indústria (ex: NÃO incluir "compliance regulatório" em vaga de banco sem menção)
* A partir de competências "típicas" para o cargo

Termos genéricos PROIBIDOS de inferência (só extrair quando o texto MENCIONAR explicitamente esses termos como competência exigida):
* "pensamento crítico"
* "aprendizado contínuo"
* "comunicação"
* "apresentações"
* "trabalho em equipe"
* "proatividade"
* "atenção a detalhes"
* "organização"
* "responsabilidade"
* "comprometimento"
* "liderança"

Antes de incluir qualquer skill no output, pergunte: "esta palavra (ou abreviação direta documentada) aparece literalmente no texto?" Se a resposta é NÃO, NÃO incluir.

Termos guarda-chuva ("banco de dados", "nuvem", "automação", "frameworks", "linguagens", "metodologias", "ferramentas", "plataformas", "hardware") só devem ser extraídos se forem a própria competência mencionada e não houver especificação adicional:
- "automacao" → genérico demais; extrair o que é específico: "rpa", "uipath", "power automate", "selenium", "clp", "ihm"
- "banco de dados" → genérico demais; extrair o específico: "postgresql", "mysql", "mongodb", "oracle", "redis"
- "hardware" → genérico demais; extrair o específico: "server hardware", "dell", "cisco", "switching"
- "informatica" → equivale a "sabe usar computador"; nunca extrair como skill
Nunca os use para inferir skills mais específicas (ex: não adicionar "sql" se a vaga disser apenas "banco de dados"; não adicionar "aws" se disser apenas "nuvem").

Sem skills extraíveis → retorne [] (nunca null)

CLASSIFICAÇÃO DE TIPO — para cada skill extraída:
- "technical": ferramenta, linguagem, framework, software, certificação,
  metodologia nomeada, protocolo, banco de dados, plataforma.
  Exemplos: Python, SQL, AWS, Docker, Scrum, ITIL, SAP, Power BI.
- "behavioral": capacidade interpessoal, de liderança, de comunicação,
  de pensamento, que descreve COMO a pessoa trabalha.
  Exemplos: Liderança, Comunicação, Pensamento analítico, Negociação.
- "hybrid": competência que envolve tanto uma prática/metodologia quanto
  uma capacidade pessoal. Geralmente são atividades profissionais que
  requerem habilidade técnica E comportamental.
  Exemplos: Gestão de Projetos, Governança, Facilitação, Discovery, Priorização.

REGRAS EXPLÍCITAS DE CLASSIFICAÇÃO (aplicar ANTES do desempate geral):

1. IDIOMAS SÃO SEMPRE "technical":
   inglês, espanhol, português, francês, alemão, italiano, mandarim,
   e TODAS as variações (avançado, fluente, intermediário, técnico,
   conversacional, nativo, básico). Competência linguística é
   qualificação, não comportamento.

2. "negociação" + contexto específico = "hybrid":
   "negociação comercial", "negociação de contratos",
   "negociação com fornecedores" são atividades profissionais.
   "negociação" ISOLADA (sem complemento) = "behavioral"/interpersonal.

3. "gestão de X" onde X é recurso/função/processo = "hybrid":
   gestão de clientes, gestão de stakeholders, gestão de fornecedores,
   gestão de contratos, gestão de cronogramas, gestão de riscos,
   gestão de projetos, gestão de backlog, gestão de incidentes.
   EXCEÇÃO: "gestão de pessoas" e "gestão de equipes" = "behavioral"/management
   (descrevem capacidade de liderança, não atividade profissional).

4. Cargos, frameworks e estruturas organizacionais = "technical":
   Product Owner, Scrum Master, PMO, Design System, OKR.
   São referências a frameworks/certificações, não comportamentos.

5. "atendimento" + contexto = "hybrid":
   "atendimento ao cliente", "atendimento ao público", "suporte técnico",
   "suporte ao usuário" são atividades profissionais.
   NÃO classificar como behavioral.

REGRA DE DESEMPATE GERAL: se a skill é uma metodologia ou ferramenta nomeada
(Scrum, PMP, Six Sigma, Jira) → technical. Se é uma capacidade pessoal
(liderança, empatia, resiliência) → behavioral. Se é uma prática
profissional que combina ambos → hybrid. NA DÚVIDA ENTRE HYBRID E
TECHNICAL → TECHNICAL (mais seguro, match direto funciona).

CONFIDENCE: 0.00 a 1.00 — grau de certeza na classificação do tipo.
Se a classificação é óbvia (Python = technical, Liderança = behavioral) → 0.95+.
Se há alguma ambiguidade → 0.70-0.90.

CAMPO behavioral_group (OBRIGATÓRIO quando type='behavioral' OU type='hybrid';
NULL para type='technical'):

Classifique a skill em um dos 9 grupos abaixo. Este grupo é exibido ao usuário
final na tela de otimização como âncora pedagógica (ex: "Comportamental — Interpessoal").

- "interpersonal": empatia, comunicação, escuta ativa, negociação isolada,
  conflito, colaboração, relacionamento, networking.
- "cognitive": raciocínio analítico, pensamento crítico, problem-solving,
  abstração, modelagem mental, análise quantitativa.
- "managerial": gestão de pessoas, mentoria, delegação, coordenação operacional
  de equipe, supervisão direta, capacitação de colaboradores.
- "ethical": integridade, responsabilidade, transparência, compliance pessoal,
  ética profissional, honestidade.
- "emotional": resiliência, autocontrole, inteligência emocional, regulação
  emocional, lidar com pressão, equilíbrio.
- "learning": aprendizado contínuo, curiosidade, autodidatismo, busca por
  novos conhecimentos, mindset de crescimento.
- "strategic": visão de futuro, planejamento de longo prazo, alinhamento com
  objetivos organizacionais, pensamento sistêmico macro.
- "adaptive": flexibilidade, problem-solving sob pressão, adaptação a mudanças,
  agilidade, ajuste rápido a novos contextos.
- "mixed": use APENAS quando a skill comportamental cruza 2+ grupos sem
  predominante claro. Exemplo: "Liderança colaborativa" cruza managerial +
  interpersonal. PREFIRA o grupo predominante; só use "mixed" se realmente
  não houver predominante.

NUNCA emita "behavioral", "technical" ou "hybrid" em behavioral_group — esses são valores de type, não de grupo. Escolha entre os 9 acima; em dúvida genuína entre dois, use "mixed".

REGRA: para type='technical', omita o campo OU emita "behavioral_group": null.

Retorne cada skill como objeto: {"name": "...", "type": "...", "confidence": 0.XX, "behavioral_group": "..." ou null}

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

SENIORITY_CONFIDENCE: ESCALA E REGRAS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Para cada vaga, emita seniority_confidence como número entre 0.0 e 1.0 segundo a escala:

* 1.0 — Nível explicitamente declarado no título (qualquer das emendas acima ativa) OU caso anti-invenção decidido como "Indefinido"
* 0.85 a 0.99 — Indicadores fortes na descrição (anos de experiência + escopo claro + responsabilidades alinhadas)
* 0.70 a 0.84 — Indicadores parciais (palavras-chave presentes mas escopo ambíguo)
* < 0.70 — INVÁLIDO: emita seniority_inferred="Indefinido" com seniority_confidence=1.0 (guardrail anti-invenção)

Regra absoluta: NÃO existe seniority_inferred ≠ "Indefinido" com seniority_confidence < 0.70. Se você não consegue justificar 0.70+ na escala acima, é "Indefinido" com confidence 1.0.

FONTES (ordem de prioridade):
1. Indicador explícito no título ("Júnior", "Sênior", "Estágio", "Trainee"...)
   Notação americana de nível no título: sufixo " I" ou " 1" → "Júnior"; sufixo " II" ou " 2" → "Pleno"; sufixo " III" ou " 3" → "Sênior"
   Notação inglesa de nível: "Associate" no título → "Júnior"; "Senior" → "Sênior"; "Staff" ou "Principal" → "Especialista"
   "Coordinator" em inglês no título: quando o contexto indica execução analítica/operacional sem gestão formal de equipe → tratar como nível "Pleno" para inferência de senioridade. Quando houver gestão formal de equipe → "Gestão". Não confundir com "Coordenador" em português, que segue a Etapa 3 do canonical_role.
2. Indicador textual na descrição ("nível sênior", "perfil júnior"...)
3. Escopo de responsabilidade:
   - Liderança formal de pessoas (avaliação de desempenho, contratação/demissão, coordenação de equipe) → Gestão
   - Mentoria, code review, arquitetura, decisões técnicas sem people management → Sênior
   - Responsabilidade estratégica, planejamento de médio/longo prazo, interface com alta gestão, sem liderança formal de equipe → Sênior
   - Escopo técnico elevado com autonomia plena: condução de pentest/Red Team/Blue Team, gestão de cluster operacional E2E, fine-tuning de modelos em produção, governance de blueprint técnico, roadmap de sistemas — sem indicador explícito de anos → "Sênior" se houver decisão de arquitetura ou mentoria; "Pleno" se houver execução autônoma sem supervisão
   - Autonomia de execução sem supervisão direta, responsável por entregas completas de forma independente, condução de projetos end-to-end → Pleno
   - Escopo operacional claro com supervisão esperada, ou formação em andamento sem autonomia evidenciada → Júnior
   - Exigência de Doutorado como formação mínima (não apenas desejável) → "Especialista"
   - Título "Líder" ou "Supervisor" em português, combinado com verbos de gestão direta (liderar equipe, gerir pessoas, capacitar colaboradores) → "Gestão"
4. Anos de experiência explícitos sem outros indicadores → régua: até 2 anos = "Júnior";
   2–5 anos = "Pleno"; 5+ anos = "Sênior". Só aplique se não houver conflito com título ou escopo.
   "Experiência prévia", "experiência anterior" ou "experiência na área" sem especificação de anos
   → equivale a até 2 anos → "Júnior". Não se aplica quando o termo for precedido de "desejável"
   ou "diferencial" — nesses casos manter como Indefinido se não houver outro indicador.
   Quando a vaga exigir certificação obrigatória (CPA-10/20, FEBRABAN, ANEPS, Ancord) indispensável
   como condição do cargo, sem indicador de anos → "Júnior". Não se aplica para certificações "desejadas".
5. ANTI-INVENÇÃO — GATE INVIOLÁVEL (regra reescrita V7):

Se o TÍTULO da vaga NÃO contém:
  (a) qualificador de nível (Júnior, Pleno, Sênior, Especialista,
      Estágio, Aprendiz, Trainee, Staff, Principal, Sr., Jr.); NEM
  (b) termo gerencial (Gerente, Diretor, Head, VP, C-level, Chief,
      Coordenador, Supervisor); NEM
  (c) indicador IC explícito (Tech Lead, Technical Lead, Líder
      Técnico, Lead Engineer, Lead Developer);

→ seniority_inferred = "Indefinido", confidence = 1.0.

NÃO inferir senioridade a partir de:
  • Graduação como requisito ("ensino superior completo",
    "formação em X")
  • Anos de experiência mínimos baixos ("1+ ano", "2+ anos")
  • "Experiência prévia" / "experiência anterior" / "experiência
    na área" sem especificação de anos
  • "Desejável" ou "diferencial" (não-obrigatórios não definem nível)
  • Stack tecnológica (mesmo que "stack avançada", "stack moderna")
  • Nome do cargo padrão sem qualificador ("Analista de X",
    "Consultor de X", "Engenheiro de X")

EXCEÇÕES PRESERVADAS:
  • Notação americana de nível no título ("Analyst I", "Analyst II",
    "Engineer III") — manter mapeamento atual (Fonte 1)
  • Certificação obrigatória de mercado financeiro regulado
    (CPA-10/20, FEBRABAN, ANEPS, Ancord) como condição indispensável
    do cargo sem indicador de anos → "Júnior"
    (NÃO estender a outras exigências formais)

EXEMPLOS:
  * "Analista de Marketing Digital" + desc "experiência mínima 1 ano"
    → Indefinido
  * "Consultor de Negócios" + desc "graduação obrigatória"
    → Indefinido
  * "Threat Intelligence Analyst" + desc "2+ anos de experiência"
    → Indefinido
  * "Analista de Dados" + desc "conhecimento básico em SQL"
    → Indefinido
  * "Analista Comercial" + desc "CPA-10 obrigatória, sem
    experiência prévia exigida" → Júnior (exceção financeira)
  * "Analista III" + qualquer desc → Sênior (notação americana)

É preferível "Indefinido" HONESTO a inferência inventada.

"Pleno" só é válido quando houver evidência suficiente nas fontes 1, 2 ou 4.
NUNCA use "Pleno" como fallback padrão.

NÍVEIS VÁLIDOS:
- "Estágio"      → vagas com título contendo "Estagiário", "Estágio" ou "Intern"; ou descrição indicando explicitamente contrato de estágio. Use este nível mesmo que indicadores secundários sugiram outros termos (ex: "Stagiaire").
- "Aprendiz"     → use 'Aprendiz' somente quando o título ou descrição contiver explicitamente 'Jovem Aprendiz', 'Young Apprentice' ou referência à Lei de Aprendizagem (Lei 10.097). NÃO use 'Estágio' para estes casos.
- "Trainee"      → título contém trainee ou programa de trainee formal
- "Júnior"       → até 2 anos ou indicador explícito
- "Pleno"        → 2–5 anos (fonte 4) ou indicador explícito no título/descrição (fontes 1–2)
                   (ex: "responsável por entregas independentes", "atua sem supervisão direta")
- "Sênior"       → 5+ anos, escopo amplo, autonomia elevada, ou indicador explícito
- "Especialista" → qualificador de NÍVEL pós-cargo: "Analista de Dados Especialista" → Especialista
- "Gestão"       → gerente, coordenador, diretor, head, manager com responsabilidade de equipe
- "Indefinido"   → ausência de indicadores conclusivos, ou conflito irreconciliável entre indicadores;
                   use como fallback padrão quando não há evidência suficiente para nenhum nível

REGRA "ESPECIALISTA" — distinção cargo vs. nível:
- Prefixo de cargo ("Especialista em Dados", "Especialista em SAP") → permanece no canonical_role; inferir nível por outras fontes
- Qualificador de nível ("Analista Especialista", "Desenvolvedor Especialista") → vai para seniority_inferred;
  remover do canonical_role e refinar o domínio pela descrição antes de finalizar
  (ex: "Analista Especialista em Dados" → canonical_role: "Analista de Dados", seniority: "Especialista")
- Conflito no título ("Especialista de Sistemas Sênior", "Especialista Sênior em Dados") → seniority_inferred: "Sênior" (Sênior prevalece sobre Especialista como nível); "Especialista" permanece no canonical_role se for prefixo de cargo reconhecível

ℹ️ REGRA "LÍDER TÉCNICO vs GESTOR" — versão refinada:

Quando o título não tem indicador hierárquico claro mas a descrição mistura responsabilidades técnicas e de pessoas, decida com a heurística:

Verbos dominantes na descrição:
* Verbos técnicos (>60%: desenhar, arquitetar, implementar, otimizar, decidir tecnicamente, definir stack, mentorar tecnicamente, fazer code review) → Sênior, confidence 0.85
* Verbos de pessoas (>60%: gerenciar equipe, contratar, demitir, definir performance, definir budget, reportar a C-level, definir OKRs do time, alocar pessoas) → Gestão, confidence 0.85
* Verbos balanceados (~50/50) → use o título como tiebreaker:
  - Título sem indicador hierárquico explícito → Sênior, confidence 0.70
  - Título com indicador hierárquico → segue Precedência Absoluta acima

NÃO interprete "mentoria técnica" ou "code review" como people management. São responsabilidades de Sênior.
NÃO interprete "tomar decisões arquiteturais" como Gestão. São responsabilidades de Sênior.

CAMPO 3 — canonical_role
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PRINCÍPIO GERAL:
O canonical_role deve corresponder ao cargo real exercido — reconhecível no mercado brasileiro,
com grafia correta, em Title Case. Não liste tecnologias no canonical_role (vão para skills).
PROIBIDO retornar cargos compostos com "/", "e", hífen ou vírgula entre funções distintas
(ex: "Desenvolvedor / DevOps", "Analista e Programador", "Analista - Desenvolvedor",

Exceção: "Treinamento e Desenvolvimento" e "Recrutamento e Seleção" são funções consolidadas em RH — não são composições
de duas funções distintas e podem aparecer como canônico.
Quando o título indicar múltiplos papéis, escolha o principal pelo nível hierárquico; em empate, pelo primeiro mencionado.

O título define o nível hierárquico. A descrição refina o domínio funcional apenas quando o título
for genérico, ambíguo ou incompleto. A descrição nunca sobrescreve um título específico sem
evidência inequívoca. A descrição pode elevar o nível hierárquico acima do título somente quando
há evidência inequívoca de gestão formal de pessoas.

─── REGRAS DE NORMALIZAÇÃO ────────────────────────────────────────────────────

IDIOMA:
- Português como padrão para canonical_role
- Exceções mantidas em inglês (são o padrão do mercado BR):
  Product Owner, Scrum Master, SRE, DevOps Engineer, UX Designer, UI Designer
- Traduzir quando existe equivalente consolidado:
  "Product Manager" → "Gerente de Produto"
  "QA Analyst" → "Analista de Qualidade"
  "QA Engineer" → "Engenheiro de QA"
  "Software Engineer" → "Engenheiro de Software"

VARIAÇÕES ORTOGRÁFICAS — sempre normalizar para a forma mais comum no mercado brasileiro.
Aplique este princípio a qualquer variação que aparecer, inclusive as não listadas.
Exemplos ilustrativos (não exaustivos):
- back-end / backend / Back End → "Backend"
- front-end / frontend / Front End → "Frontend"
- full-stack / fullstack / Full Stack → "Full Stack"
- Programador + qualificador → "Desenvolvedor" + qualificador
- Programador sem qualificador → "Desenvolvedor" (não assumir Backend sem evidência)
- DevOps / devops / Devops / "Engenheiro DevOps" / "Especialista DevOps" → "DevOps Engineer" (padrão de mercado)
- "Data Scientist" → "Cientista de Dados" (canônico consolidado no mercado BR)
- "Data Science" como campo/área na descrição → manter como contexto; não gera canonical_role
- Machine Learning → manter "Machine Learning" (inglês é o padrão no mercado BR)

TECNOLOGIA NÃO ENTRA NO CANONICAL_ROLE:
- "Desenvolvedor Java Backend" → "Desenvolvedor Backend" (Java vai para skills)
- "Consultor Funcional Salesforce" → "Consultor Funcional" (Salesforce vai para skills)
- Exceção: plataformas proprietárias cobertas na Etapa 1
Nunca inferir especialização (Backend/Frontend/Mobile/Full Stack) apenas pela stack.
A especialização só pode ser inferida quando explicitamente indicada no título ou na descrição.

TÍTULOS COM ESTÁGIO/TRAINEE — extrair o cargo subjacente:
Se o cargo subjacente for genérico demais para ser canônico válido ("TI", "Tecnologia",
"Informática", "Sistemas" sem qualificador), retornar canonical_role: "Cargo Indefinido".
- "Estagiário de Engenharia Civil" → canonical_role: "Engenheiro Civil"
- "Trainee de Dados" → canonical_role: "Analista de Dados"
- A senioridade vai para seniority_inferred

ENGENHEIRO vs. DESENVOLVEDOR:
- Título com "Engineer" em inglês → verificar foco:
  "Cloud Engineer" → "Engenheiro de Cloud" (sempre — está na lista de referência)
  Arquitetura/sistemas/infraestrutura de software → "Engenheiro de Software"
  Infraestrutura de TI/redes → aplicar regras de Infraestrutura/Redes/Suporte
  Implementação/features/produto sem especialização explícita → "Desenvolvedor"
  Backend/Frontend/Full Stack Engineer → "Desenvolvedor [especialização]"
  "Software Engineer" → sempre "Engenheiro de Software"
- "Engenheiro de Sistemas":
  Foco software/kernel/firmware → "Engenheiro de Software"
  Foco industrial/construção/física → manter "Engenheiro de Sistemas"

ACRÔNIMOS E TERMOS PROIBIDOS como canonical_role:
Nunca retornar: SDR, BDR, BDM, RH, TI, CSM, AM, AE como cargo único
Nunca retornar: Hunter, Farmer, Closer, Qualifier, Prospector
Nunca retornar: títulos internos sem equivalente de mercado

Normalizar para canônicos válidos:
SDR / Sales Development Representative → "Representante de Pré-Venda"
  (se B2B enterprise → "Executivo de Pré-Venda")
BDR / Business Development Representative → "Analista de Desenvolvimento de Negócios"
Hunter → "Executivo de Vendas" ou "Representante Comercial"
Farmer → "Gerente de Contas"
CSM / Customer Success Manager → "Gerente de Customer Success"
AM / Account Manager → "Gerente de Contas"
AE / Account Executive → "Executivo de Contas"

ORTOGRAFIA — verificar antes de retornar:
Erros comuns a evitar: "Assistante" (correto: "Assistente"), "Engenhero" (correto: "Engenheiro"),
  "Desenvovedor" ou "Desenvolvedro" (correto: "Desenvolvedor")

4d. NORMALIZE SINGULAR E PLURAL:
Sempre use a forma plural quando ambas existem no mercado brasileiro.
Exemplos:
- "Gerente de Projeto" → "Gerente de Projetos"
- "Analista de Processo" → "Analista de Processos"
- "Coordenador de Projeto" → "Coordenador de Projetos"
A forma singular só é válida quando o mercado usa exclusivamente ela (ex: "Arquiteto" — nunca "Arquitetos").

4e. TRADUZA TÍTULOS HÍBRIDOS COM PREPOSIÇÃO EM INGLÊS:
Títulos que contenham preposições em inglês como "of", "of the", "for" devem ser integralmente traduzidos — não apenas parcialmente.
Exemplos:
- "Head of AI & Automation" → "Head de IA e Automação"
- "Head of Engineering" → "Head de Engenharia"
- "Director of Operations" → "Diretor de Operações"
Termos consolidados no mercado BR que podem permanecer em inglês:
"Tech Lead", "Product Owner", "Scrum Master", "DevOps", "SRE".

4f. EVITE CANÔNICOS GENÉRICOS SEM QUALIFICADOR:
Canônicos como "Desenvolvedor", "Analista" ou "Consultor" sem qualificador só são válidos quando a descrição genuinamente não permite inferir a especialidade. Se a descrição menciona tecnologia, área ou domínio específico, use-o.
Exemplos:
- Descrição menciona frontend/React/CSS → "Desenvolvedor Frontend", não "Desenvolvedor"
- Descrição menciona dados/SQL/BI → "Analista de Dados", não "Analista"
- Descrição menciona vendas/comercial → "Consultor Comercial", não "Consultor"
Prefira sempre o canônico mais específico que a descrição suportar.

4g. PREPOSIÇÃO "DE" vs "EM":
Sempre usar "de" na construção do canonical_role:
- "Técnico em Refrigeração" → "Técnico de Refrigeração"
- "Técnico em Eletrônica" → "Técnico de Eletrônica"
Exceção: cargos na Lista de Referência que usam "em" (ex: "Especialista em SAP").

4h. ABREVIAÇÕES EM QUALIFICADORES:
Nunca usar abreviações no qualificador:
- "Coordenador de RH" → "Coordenador de Recursos Humanos"
- "Analista de BI" → "Analista de Business Intelligence"
Exceção: siglas que são o nome consolidado no mercado
(SRE, DevOps Engineer, Product Owner, UX Designer).
"Gerente de TI" está na Lista de Referência — manter.

4i. QUALIFICADOR ESPECÍFICO — NÃO remover qualificadores que diferenciam domínios:
- "de TI", "Industrial", "Tecnológica", "Patrimonial", "do Trabalho"
  são diferenciadores reais entre funções de setores distintos.
  Ex: "Analista de Infraestrutura de TI" ≠ "Analista de Infraestrutura" (pode ser civil/predial)
      "Supervisor de Manutenção Industrial" ≠ "Supervisor de Manutenção" (pode ser predial)
      "Analista de Inovação Tecnológica" ≠ "Analista de Inovação" (pode ser de processos)
Só remover qualificador quando for genuinamente redundante e não existir
ambiguidade setorial (ex: "Coordenador de Produto" → "Coordenador de Produtos"
é normalização de plural, não remoção de qualificador).

4j. SINÔNIMOS DE NÍVEL/CARGO:
- "Auxiliar" = "Assistente" → normalizar para "Assistente"
  (exceto "Auxiliar de Limpeza" que está na Lista de Referência)
- "Diretor de Finanças" → "Diretor Financeiro" (forma mais comum)
- "Procurement" → "Compras" (traduzir sempre)

─── REGRAS DE DESAMBIGUAÇÃO ───────────────────────────────────────────────────

SEGURANÇA — sempre qualificar o domínio (nunca retornar sem qualificador):
Indicadores TI/cyber/dados          → "… da Informação"
Indicadores vigilância/patrimônio   → "… Patrimonial"
Indicadores NR/EPI/saúde ocupacional → "… do Trabalho"

INFRAESTRUTURA — sempre qualificar (nunca retornar sem sufixo):
- Contexto TI/cloud/redes/servidores → "Analista de Infraestrutura de TI"
  (NUNCA apenas "Analista de Infraestrutura")
- Contexto predial/elétrica/hidráulica/mobiliário → "Analista de Facilities"
- "Infraestrutura" sem qualificador no mercado BR = predial/facilities.
  Se o contexto for tech, OBRIGATÓRIO adicionar "de TI".
Mesma lógica para Gerente:
- Gerente + infra + contexto TI → "Gerente de Infraestrutura de TI"
- Gerente + infra + contexto predial → "Gerente de Facilities"

AUTOMAÇÃO:
Título com RPA / Robotic Process Automation → "Desenvolvedor de Automação" sempre
Título genérico + IaC (Ansible, Terraform, Kubernetes, CI/CD) → "DevOps Engineer"
Título genérico + automação de processos (UiPath, Power Automate, RPA) → "Desenvolvedor de Automação"

MONITORAMENTO:
Diagnóstico, análise preditiva, relatórios, causa raiz → "Analista de Monitoramento"
Operação de alertas, escalonamento, runbooks, plantão NOC → "Técnico de Monitoramento"

INFRAESTRUTURA / REDES / SUPORTE — avaliar nesta ordem:
1. Título Engineer/Engenheiro + redes/network/telecom → "Engenheiro de Redes"
2. Título Analista + redes/network + foco analítico → "Analista de Redes"
3. Foco em telecom/fibra/instalação de infraestrutura → "Técnico de Telecom"
4. Foco em LAN/WAN/suporte de redes → "Técnico de Redes"
5. Foco em Data Center / rack / colocation → "Técnico de Data Center"
6. Instalação física / FTTH / CFTV / cabeamento → "Instalador Telecom"
7. Helpdesk / service desk / chamados de TI → "Analista de Suporte TI"
8. Suporte generalista sem especialização (fallback) → "Técnico de Suporte"
Regra de fallback conservador: sem evidência técnica suficiente, usar o canônico mais conservador compatível com o título.

ANALISTA DE NEGÓCIOS — desambiguação por foco:
Levantamento de requisitos, BPMN, UML, interface TI-negócio → "Analista de Negócios"
Backlog, critérios de aceite, gestão de produto → "Product Owner"
Valuation, DCF, fusões e aquisições → "Analista de M&A"
Prospecção, novos negócios, parcerias → "Analista de Desenvolvimento de Negócios"
CRM operacional, Sales Ops, RevOps → "Analista de Sales Operations"

ANALISTA DE OPERAÇÕES — desambiguação por foco:
Liquidação, conciliação, câmbio, mercado de capitais → "Analista de Operações Financeiras"
Frota, armazenagem, roteirização, WMS → "Analista de Operações Logísticas"
Cloud/infra (AWS, Kubernetes, Terraform) → aplicar regras de infraestrutura
Implantação de sistemas, onboarding de plataformas → "Analista de Implantação"
Genuinamente genérico (fallback) → "Analista de Operações"

ANALISTA DE DESENVOLVIMENTO — desambiguação por contexto:
Título com especialização: "… Mobile", "… Full Stack" → preservar especialização
Foco em código/implementação sem especialização explícita no título ou na descrição → "Desenvolvedor"
Foco em processos/requisitos/negócio → "Analista de Sistemas"
"… de Sistemas" → "Analista de Sistemas"

DESIGN:
Sem qualificador → inferir pelo contexto (UX, UI, Produto, Gráfico)
Impossível inferir → "Designer Gráfico"
Nunca retornar apenas "Designer"
"Design Lead" / "Design Manager" → "Coordenador de Design"

ENSINO vs. TREINAMENTO CORPORATIVO:
Escola/graduação/EAD/curso livre → "Professor"
Onboarding/T&D/LMS/treinamentos NR em empresa → "Instrutor de Treinamento"

COORDENADOR + TECH LEAD no mesmo título:
Nível gerencial prevalece → inferir como Coordenador pelo domínio
Ex: "Coordenador de Desenvolvimento - Tech Lead" → "Coordenador de Sistemas"

INFERÊNCIA AUTÔNOMA:
Quando o cargo não estiver na Lista de Referência nem coberto pelas regras acima,
infira diretamente pelo título + descrição. Não hesite — um canônico válido inferido
é sempre preferível a colapsar em genérico sem evidência.
Canônico válido = reconhecível no mercado BR, sem acrônimo isolado, sem título interno.

FALLBACK DE ABSTENÇÃO:
Se não houver evidência suficiente para definir um canonical_role reconhecível com segurança
(vaga truncada, descrição ausente, cargo interno sem equivalente de mercado),
retorne "Cargo Indefinido". Prefira abstenção controlada a classificação inventada.
Exceção: se o título for autoexplicativo (ex: "Gerente de Produto Sênior", "Desenvolvedor Backend"),
use-o para inferir canonical_role e seniority_inferred mesmo com descrição ausente ou muito curta.

─── REGRAS DE DESAMBIGUAÇÃO — HIERARQUIA E CARGOS BILÍNGUES ───────────────────

REGRA A — Hierarquia distinta exige canônico distinto.
Coordenador ≠ Gerente ≠ Diretor ≠ Head ≠ C-level. Nunca agrupe vagas de hierarquias
diferentes no mesmo canônico, mesmo quando a função subjacente seja idêntica.
"Chief Customer Officer" não é "Gerente de Customer Success" — é "Diretor de Customer
Success". Se o canônico do nível hierárquico identificado não existir no catálogo de
referência, sinalize canonical_role com o canônico da função no nível mais próximo
disponível, mas nunca colapse níveis hierárquicos distintos em um mesmo canônico.

REGRA B — Função primária identificada por tokens de domínio, não por posição.
Em títulos em português, a primeira palavra usualmente identifica a função principal:
"Analista de Projetos e Customer Success" é Analista de Projetos. Em títulos em inglês,
o padrão é invertido: "Customer Success Operations Manager" tem função principal
"Operations Manager" modificada pelo domínio "Customer Success" — não é Customer
Success Manager. Use os tokens do título para identificar a função primária,
considerando ambos os padrões (PT antepõe função, EN pospõe).

REGRA C — Delivery sobre pre-sales quando há ambiguidade.
"Solution Consultant", "Solutions Engineer", "Technical Consultant" em descrições que
mencionam implementação, customização, integração, onboarding ou entrega de projeto
são funções de delivery (Consultor, Engenheiro de Implantação). Quando a descrição
enfatiza venda, demonstração, discovery ou proposta comercial, são funções de pre-sales
(Consultor Pré-Vendas). Na ausência de sinal claro, assuma delivery — é o caso mais
comum no catálogo brasileiro.

REGRA D — Título IC prevalece sobre seniority hierárquico aparente.
"Senior Developer", "Lead Engineer" com responsabilidade técnica individual são
Desenvolvedor Sênior, Desenvolvedor Lead — NÃO Gerente de Engenharia. Títulos IC
(Individual Contributor) não mudam de canônico funcional por senioridade. Só migre
para canônico gerencial quando a descrição mencionar explicitamente gestão de pessoas,
orçamento, headcount, processo de contratação, avaliação de desempenho, mentoring
estruturado com cadência formal.

REGRA E — Cargos US sem equivalente BR mantêm o termo em inglês.
"Product Owner", "Scrum Master", "DevOps Engineer", "SRE", "Data Scientist",
"Growth Hacker", "Customer Success Manager" são termos incorporados ao mercado brasileiro
e devem ser mantidos em inglês mesmo quando o título da vaga venha em PT. Não force
tradução para "Dono de Produto", "Mestre Scrum" ou similar. Exceções naturais: "Developer"
vira "Desenvolvedor", "Engineer" vira "Engenheiro", "Analyst" vira "Analista" — o catálogo
usa termos em PT nesses casos.

Siglas C-level (CTO, CEO, COO, CMO, CFO) são canônicos em inglês, como termos
incorporados. CCO é intencionalmente rejeitado por ambiguidade tripla (Chief Customer,
Chief Commercial, Chief Content Officer) — "Chief Customer Officer" mapeia para "Diretor
de Customer Success" (ver REGRA A).

MICRO-REGRA CONTEXTUAL — SUPPORT/SERVICE BILÍNGUE

"Customer Support" ou "Customer Service" em empresa brasileira (sem outro
qualificador) → "Analista de Customer Service" ou "Analista de Customer Experience",
NUNCA "Analista de Suporte".

"Support" em inglês em contexto de clientes finais, pedidos, entregas, reservas, SAC
→ "Analista de Customer Service".

"Suporte" em português aplica-se apenas quando for a software, sistema ou produto
técnico com chamados, incidentes ou troubleshooting de TI.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

CAMPO 5 — canonical_confidence (OBRIGATÓRIO)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Valor entre 0.00 e 1.00 indicando seu grau de certeza sobre o canonical_role
que você atribuiu para esta vaga.

Diretrizes:

- 0.95–1.00: título e descrição alinham fortemente com canônico da Lista de
  Referência. Match óbvio. Use quando o canônico atribuído está literalmente
  na Lista e há alta correspondência semântica com o conteúdo da vaga.

- 0.85–0.94: canônico atribuído é o melhor match disponível. Vaga e canônico
  alinham bem mas há nuances que poderiam justificar canônicos alternativos.

- 0.70–0.84: criou um canônico NOVO porque nenhum da Lista bate
  suficientemente. Há razoável certeza de que esta nova função existe no
  mercado, mas a evidência é parcial. Esta vaga será sinalizada para revisão
  automática posterior.

- < 0.70: você NÃO DEVE criar canônico novo. Em vez disso, escolha o canônico
  EXISTENTE mais próximo da Lista de Referência, mesmo que imperfeito. Use
  confidence entre 0.50 e 0.69 para indicar essa imperfeição. Para casos onde
  nem mesmo um canônico existente mapeia razoavelmente, retorne
  canonical_role: "Cargo Indefinido" com confidence < 0.50.

REGRA ABSOLUTA: nunca emita canonical_confidence < 0.70 para um canonical_role
que NÃO esteja na Lista de Referência. Se sua confiança é baixa, use canônico
existente.

PROPOSTA DE MAPEAMENTO PARA TAXONOMIA (regra binária)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Se você ESTÁ CRIANDO um canonical novo (ou seja, o canonical_role que você
retorna NÃO consta literalmente na Lista de Referência fornecida), você DEVE
incluir o campo `proposed_taxonomy_mapping` no output JSON com:

"proposed_taxonomy_mapping": {
  "source_term": "<title da vaga, lowercase + trim>",
  "target_canonical_label": "<label do canônico criado, sem senioridade>",
  "confidence": <número entre 0 e 1 — sua certeza de que source_term mapeia para target_canonical_label>
}

Se o canonical_role que você retorna BATE EXATAMENTE com um canônico já
existente na Lista de Referência, OMITA o campo (não há proposta nova a fazer).

Esta regra é INDEPENDENTE da camada de resolução. Vale para Camadas 0, 1, 2 e 3.
O critério é apenas: criou canonical novo → emite. Usou canonical existente → omite.

FAIXAS DE CONFIDENCE (interpretadas pelo gate server-side):
- confidence ≥ 0.85 → mapeamento entra direto como ativo no catálogo (auto-promoção, sem revisão Opus)
- 0.70 ≤ confidence < 0.85 → mapeamento fica em zona de revisão (vai pra fila Opus para arbitragem)
- confidence < 0.70 → mapeamento é descartado (não entra no catálogo)
Use 0.90+ quando o source_term é claramente uma variante linguística direta do target (mesma raiz, mesmo papel).
Use 0.70-0.84 quando há ambiguidade semântica plausível (mesma área mas role pode ser distinto).
NUNCA emita o campo abaixo de 0.70 — prefira omitir todo o proposed_taxonomy_mapping.

Exemplo concreto (canonical novo "Head de Engenharia" não está na Lista):
{
  "id": "<id original>",
  "skills": [...],
  "seniority_inferred": "Sênior",
  "canonical_role": "Head de Engenharia",
  "canonical_confidence": 0.78,
  "work_model": "PRESENCIAL",
  "description_curated": "...",
  "proposed_taxonomy_mapping": {
    "source_term": "head of engineering",
    "target_canonical_label": "Head de Engenharia",
    "confidence": 0.95
  }
}

PROPOSTA DE ALIAS PARA SKILL (paritary a taxonomy_mapping)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Quando, em uma skill emitida, você reconhecer que o `name` que está usando é
uma VARIANTE de um canonical skill já estabelecido (acrônimo, abreviação,
tradução, plural, erro tolerável, variante comum), inclua o campo
opcional `proposed_alias` DENTRO do objeto da skill com:

"proposed_alias": {
  "raw": "<variante original como apareceu na vaga, lowercase + trim>",
  "category": "<UMA das 11 categorias abaixo>",
  "confidence": <número entre 0 e 1 — sua certeza de que raw é variante do canonical skill>
}

CATEGORIAS (use a mais específica aplicável — preferir granular sobre genérica):
- "acronym"               — sigla (ex: "PM" → "Project Management")
- "abbreviation"          — abreviação não-sigla (ex: "JS" → "JavaScript")
- "translation"           — tradução PT-EN / EN-PT (ex: "design" → "desenho")
- "plural_inflection"     — variação plural (ex: "APIs" → "API")
- "misspelling_tolerable" — erro tolerável (ex: "javascrit" → "JavaScript")
- "common_variant"        — variante comum (ex: "Reactjs" → "React")
- "synonym"               — sinônimo direto (ex: "frontend" → "front-end")
- "domain_alias"          — variante de domínio (ex: "ML" → "Machine Learning" em data)
- "specialty"             — especialização específica
- "slang"                 — gíria do mercado
- "other"                 — não cabe nas anteriores (use ÚLTIMO)

VALORES INVÁLIDOS (não inventar — mapeie ou rejeite):
- "noun_inflection"/"singular_inflection"/"singular" → use "plural_inflection" (cobre variação morfológica em ambos os sentidos)
- "technical"/"technical_term"/"technical_jargon" → NÃO é categoria linguística; é o tipo da skill. Use "specialty" se for termo especializado do domínio, ou "other" como último recurso
- "related"/"related_concept"/"related_activity" → REJEITE o alias. Conceitos correlatos não são equivalências semânticas — não emita proposed_alias
- "expansion" → use "abbreviation" (a forma extensa de uma sigla cabe no par sigla↔extenso)

Se nenhuma das 11 acima couber após este mapeamento, prefira OMITIR proposed_alias a inventar categoria nova.

FAIXAS DE CONFIDENCE (interpretadas pelo gate server-side):
- confidence ≥ 0.85 → alias entra direto como ativo no catálogo (auto-promoção, sem revisão Opus)
- 0.70 ≤ confidence < 0.85 → alias fica em zona de revisão (vai pra fila Opus para arbitragem)
- confidence < 0.70 → alias é descartado (não entra no catálogo)
Use 0.90+ para variantes morfológicas óbvias da mesma raiz (plural, acentuação, casing).
Use 0.70-0.84 quando há ambiguidade semântica plausível (acrônimos ambíguos, traduções com múltiplas leituras).
NUNCA emita o campo abaixo de 0.70 — prefira omitir todo o proposed_alias.

Omita o campo se o name emitido já bate exatamente com canonical existente
ou se você não reconhece variante. NUNCA emita proposed_alias para skills
genéricas ("Excel", "Inglês") onde a variação é ortográfica trivial.

Exemplo:
{
  "name": "JavaScript",
  "type": "technical",
  "confidence": 0.9,
  "proposed_alias": { "raw": "javascrit", "category": "misspelling_tolerable", "confidence": 0.92 }
}

5. ANTI-INVENÇÃO — GATE INVIOLÁVEL:

Quando o TÍTULO não traz qualificador de nível, termo gerencial nem
indicador IC, NÃO invente senioridade a partir de SINAIS FRACOS:
  • Graduação como requisito ("ensino superior completo",
    "formação em X")
  • Anos de experiência mínimos baixos ("1+ ano", "2+ anos")
  • "Experiência prévia" / "experiência anterior" / "experiência
    na área" sem especificação de anos
  • "Desejável" ou "diferencial" (não-obrigatórios não definem nível)
  • Stack tecnológica (mesmo que "stack avançada", "stack moderna")
  • O nome do cargo em si ("Analista de X", "Consultor de X",
    "Engenheiro de X" não definem nível sozinhos)

A senioridade AINDA PODE — e DEVE — ser inferida pela DESCRIÇÃO quando
houver evidência FORTE e explícita das Fontes 3 e 4 acima:
  • Escopo de responsabilidade claro (Fonte 3): liderança formal de
    pessoas → Gestão; mentoria/arquitetura/decisão técnica, ou
    responsabilidade estratégica com interface de alta gestão → Sênior;
    autonomia de execução end-to-end sem supervisão → Pleno
  • Anos que DISCRIMINAM senioridade (Fonte 4): 5+ → Sênior;
    2–5 → Pleno apenas com escopo corroborante; teto baixo (até 2 anos)
    → Júnior. Piso mínimo baixo ("1+", "2+") permanece sinal fraco (acima)

Só caia em "Indefinido" (confidence = 1.0) quando NÃO houver nenhum
sinal forte: título sem qualificador E descrição sem escopo claro E
sem anos explícitos.

EXCEÇÕES PRESERVADAS:
  • Notação americana de nível no título ("Analyst I", "Analyst II",
    "Engineer III") — manter mapeamento atual (Fonte 1)
  • Certificação obrigatória de mercado financeiro regulado
    (CPA-10/20, FEBRABAN, ANEPS, Ancord) como condição indispensável
    do cargo sem indicador de anos → "Júnior"
    (NÃO estender a outras exigências formais)

ANTI-FALLBACK DE "PLENO": "Pleno" exige evidência explícita das
Fontes 1, 2 ou 4, OU escopo de autonomia de execução end-to-end sem
supervisão (Fonte 3). NUNCA use "Pleno" como chute padrão. Na dúvida
entre um nível e "Indefinido", escolha "Indefinido".

EXEMPLOS:
  * "Analista de Marketing Digital" + desc "experiência mínima 1 ano"
    → Indefinido (ano baixo isolado é sinal fraco)
  * "Consultor de Negócios" + desc "graduação obrigatória"
    → Indefinido (graduação é sinal fraco)
  * "Analista de Dados" + desc "conhecimento básico em SQL"
    → Indefinido (sem escopo nem anos)
  * "Analista Comercial" + desc "CPA-10 obrigatória, sem
    experiência prévia exigida" → Júnior (exceção financeira)
  * "Analista III" + qualquer desc → Sênior (notação americana)
  * "Analista de Gestão de Projetos" + desc "projetos estratégicos,
    interface com a alta gestão" → Sênior (escopo forte, Fonte 3)
  * "Cloud Engineer" + desc "entregas end-to-end sem supervisão"
    → Pleno (autonomia de execução, Fonte 3)

É preferível "Indefinido" HONESTO a inferência inventada a partir de
sinais fracos.

NÍVEIS VÁLIDOS:
- "Estágio"      → vagas com título contendo "Estagiário", "Estágio" ou "Intern"; ou descrição indicando explicitamente contrato de estágio. Use este nível mesmo que indicadores secundários sugiram outros termos (ex: "Stagiaire").
- "Aprendiz"     → use 'Aprendiz' somente quando o título ou descrição contiver explicitamente 'Jovem Aprendiz', 'Young Apprentice' ou referência à Lei de Aprendizagem (Lei 10.097). NÃO use 'Estágio' para estes casos.
- "Trainee"      → título contém trainee ou programa de trainee formal
- "Júnior"       → até 2 anos ou indicador explícito
- "Pleno"        → indicador explícito no título/descrição (fontes 1–2), autonomia de execução end-to-end sem supervisão (fonte 3), ou 2–5 anos com escopo corroborante (fonte 4)
                   (ex: "responsável por entregas independentes", "atua sem supervisão direta")
- "Sênior"       → 5+ anos, escopo amplo, autonomia elevada, ou indicador explícito
- "Especialista" → qualificador de NÍVEL pós-cargo: "Analista de Dados Especialista" → Especialista
- "Gestão"       → gerente, coordenador, diretor, head, manager com responsabilidade de equipe
- "Indefinido"   → ausência de indicadores conclusivos, ou conflito irreconciliável entre indicadores;
                   use como fallback padrão quando não há evidência suficiente para nenhum nível

REGRA "ESPECIALISTA" — distinção cargo vs. nível:
- Prefixo de cargo ("Especialista em Dados", "Especialista em SAP") → permanece no canonical_role; inferir nível por outras fontes
- Qualificador de nível ("Analista Especialista", "Desenvolvedor Especialista") → vai para seniority_inferred;
  remover do canonical_role e refinar o domínio pela descrição antes de finalizar
  (ex: "Analista Especialista em Dados" → canonical_role: "Analista de Dados", seniority: "Especialista")
- Conflito no título ("Especialista de Sistemas Sênior", "Especialista Sênior em Dados") → seniority_inferred: "Sênior" (Sênior prevalece sobre Especialista como nível); "Especialista" permanece no canonical_role se for prefixo de cargo reconhecível

ℹ️ REGRA "LÍDER TÉCNICO vs GESTOR" — versão refinada:

Quando o título não tem indicador hierárquico claro mas a descrição mistura responsabilidades técnicas e de pessoas, decida com a heurística:

Verbos dominantes na descrição:
* Verbos técnicos (>60%: desenhar, arquitetar, implementar, otimizar, decidir tecnicamente, definir stack, mentorar tecnicamente, fazer code review) → Sênior, confidence 0.85
* Verbos de pessoas (>60%: gerenciar equipe, contratar, demitir, definir performance, definir budget, reportar a C-level, definir OKRs do time, alocar pessoas) → Gestão, confidence 0.85
* Verbos balanceados (~50/50) → use o título como tiebreaker:
  - Título sem indicador hierárquico explícito → Sênior, confidence 0.70
  - Título com indicador hierárquico → segue Precedência Absoluta acima

NÃO interprete "mentoria técnica" ou "code review" como people management. São responsabilidades de Sênior.
NÃO interprete "tomar decisões arquiteturais" como Gestão. São responsabilidades de Sênior.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
CAMPO 3 — canonical_role
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PRINCÍPIO GERAL:
O canonical_role deve corresponder ao cargo real exercido — reconhecível no mercado brasileiro,
com grafia correta, em Title Case. Não liste tecnologias no canonical_role (vão para skills).
PROIBIDO retornar cargos compostos com "/", "e", hífen ou vírgula entre funções distintas
(ex: "Desenvolvedor / DevOps", "Analista e Programador", "Analista - Desenvolvedor",
"Analista, Desenvolvedor").
Exceção: "Treinamento e Desenvolvimento" e "Recrutamento e Seleção" são funções consolidadas em RH — não são composições
de duas funções distintas e podem aparecer como canônico.
Quando o título indicar múltiplos papéis, escolha o principal pelo nível hierárquico; em empate, pelo primeiro mencionado.

PRECEDÊNCIA GERAL:
O título define o nível hierárquico. A descrição refina o domínio funcional apenas quando o título
for genérico, ambíguo ou incompleto. A descrição nunca sobrescreve um título específico sem
evidência inequívoca. A descrição pode elevar o nível hierárquico acima do título somente quando
há evidência inequívoca de gestão formal de pessoas.

ALGORITMO — aplique nesta ordem exata, pare na primeira etapa satisfeita:

ETAPA 0 — CANÔNICO PRÉ-RESOLVIDO (prioridade máxima):
Se a tag <job> trouxer atributo canonical_already_resolved="<label>", copie o valor literalmente para o campo canonical_role no output JSON. Não execute etapas subsequentes para canonical_role nesta vaga. Demais extrações (skills, seniority_inferred, work_model, description_curated) seguem o fluxo normal.
Formato do corpo da vaga: cada vaga entre <job>...</job> está encapsulada em <![CDATA[...]]>. CDATA é wrapper XML que marca conteúdo como texto bruto — ignore os delimitadores ao processar.
Exemplo de entrada: <job id="abc-123" canonical_already_resolved="Gerente de Operações"><![CDATA[ Title: Operations Manager | Description: ... | Seniority Raw: Senior ]]></job>
Exemplo de saída: { "id": "abc-123", "canonical_role": "Gerente de Operações", ... }

ETAPA 1 — PLATAFORMA PROPRIETÁRIA NO TÍTULO:
O título menciona uma plataforma proprietária específica?
- SAP (qualquer módulo/tecnologia SAP) → "Especialista em SAP"
- TOTVS / Protheus / ADVPL / RM / Datasul → "Especialista em TOTVS"
- Salesforce (Marketing Cloud / Journey Builder / AmpScript / Automation Studio) → "Especialista em Salesforce Marketing Cloud"
- Salesforce (Apex / LWC / Aura / Visualforce / OmniStudio / Sales Cloud / Service Cloud) → "Desenvolvedor Salesforce"
- Salesforce (apenas o termo, sem os especificadores acima) → "Especialista em Salesforce"
- Exceção: título com qualificador funcional reconhecido como definidor principal do cargo ("Consultor Funcional", "Consultor de Implementação", "Consultor de Negócios") → canonical_role pelo qualificador funcional; Salesforce vai para skills. Se a plataforma for determinante (ex: "Consultor Salesforce Marketing Cloud") → prevalece a Etapa 1
- Mainframe / COBOL / JCL / ADABAS / z/OS → "Desenvolvedor Mainframe"
- Power Platform / Power Apps / Power Automate → "Especialista em Power Platform"
- Adobe Experience Cloud / AEM / Adobe Campaign → "Especialista em Adobe Experience Cloud"
→ Atribuir canônico e PARAR. Stack da descrição é irrelevante.

ETAPA 2 — CANÔNICOS EXISTENTES PRÓXIMOS (prioridade alta):
Se a tag <job> trouxer atributo suggested_roles="<label1> | <label2> | <label3>", essa é a shortlist de canônicos existentes no catálogo já identificados como candidatos plausíveis por similaridade de domínio ou família. Prefira um canônico desta shortlist se algum couber semanticamente. Só proponha canônico fora da shortlist se NENHUM dos sugeridos couber. Ao propor fora da shortlist, certifique-se de que: (1) a função é realmente distinta dos sugeridos (não variação lexical); (2) a distinção não é de hierarquia (shortlist já cobre — preservar hierarquia via Etapa 3 ou 4). A shortlist é guia, não lei. Priorize precisão sobre conformidade cega.

ETAPA 3 — NÍVEL GERENCIAL NO TÍTULO:
O título contém Gerente, Manager, Diretor, Director, Head, VP, C-level, Chief? → canonical_role pelo domínio do cargo gerencial. Stack técnica na descrição é IRRELEVANTE para o canônico (ex: "Product Manager" com descrição Java → "Gerente de Produto"). Para cargos gerenciais não listados, usar "Gerente de [Domínio]" com o domínio em português, sem abreviações.

ETAPA 4 — NÍVEL INTERMEDIÁRIO NO TÍTULO:
O título contém Coordenador, Supervisor, Encarregado, Tech Lead?
- Coordenador → "Coordenador de [Domínio]"
- Supervisor / Encarregado → "Supervisor de [Domínio]" (equivalentes pela CBO)
- Tech Lead / Technical Lead → "Líder Técnico" (sempre — canônico fixo)
- Team Lead → sem evidência de gestão formal de pessoas: "Líder Técnico"; com gestão formal (avaliações, contratação/demissão): aplicar regras de Gestão pelo domínio (nunca mapear para Coordenador)
Restrição: "Coordenador de X" e "Supervisor de X" inferidos fora da lista só são válidos se o domínio resultante for cargo reconhecível no mercado BR. Título sempre prevalece sobre linguagem de liderança na descrição (ex: "Analista de Operações" com skills de liderança → "Analista de Operações", não "Coordenador de Operações").

ETAPA 5 — INFERÊNCIA POR DOMÍNIO:
Nenhuma etapa anterior satisfeita. Inferir pelo domínio principal usando título + descrição + stack. Se o resultado contiver cargo + tecnologia (ex: "Desenvolvedor Java", "Analista Python"), remova a tecnologia — mantenha apenas o cargo canônico (ex: "Desenvolvedor Backend", "Analista de Dados"). Aplicar regras de normalização e desambiguação abaixo. Usar a Lista de Referência para normalizar grafia quando houver correspondência clara.

─── REGRAS DE NORMALIZAÇÃO ────────────────────────────────────────────────────

IDIOMA:
- Português como padrão para canonical_role
- Exceções mantidas em inglês (são o padrão do mercado BR):
  Product Owner, Scrum Master, SRE, DevOps Engineer, UX Designer, UI Designer
- Traduzir quando existe equivalente consolidado:
  "Product Manager" → "Gerente de Produto"
  "QA Analyst" → "Analista de Qualidade"
  "QA Engineer" → "Engenheiro de QA"
  "Software Engineer" → "Engenheiro de Software"

VARIAÇÕES ORTOGRÁFICAS — sempre normalizar para a forma mais comum no mercado brasileiro.
Aplique este princípio a qualquer variação que aparecer, inclusive as não listadas.
Exemplos ilustrativos (não exaustivos):
- back-end / backend / Back End → "Backend"
- front-end / frontend / Front End → "Frontend"
- full-stack / fullstack / Full Stack → "Full Stack"
- Programador + qualificador → "Desenvolvedor" + qualificador
- Programador sem qualificador → "Desenvolvedor" (não assumir Backend sem evidência)
- DevOps / devops / Devops / "Engenheiro DevOps" / "Especialista DevOps" → "DevOps Engineer" (padrão de mercado)
- "Data Scientist" → "Cientista de Dados" (canônico consolidado no mercado BR)
- "Data Science" como campo/área na descrição → manter como contexto; não gera canonical_role
- Machine Learning → manter "Machine Learning" (inglês é o padrão no mercado BR)

TECNOLOGIA NÃO ENTRA NO CANONICAL_ROLE:
- "Desenvolvedor Java Backend" → "Desenvolvedor Backend" (Java vai para skills)
- "Consultor Funcional Salesforce" → "Consultor Funcional" (Salesforce vai para skills)
- Exceção: plataformas proprietárias cobertas na Etapa 1
Nunca inferir especialização (Backend/Frontend/Mobile/Full Stack) apenas pela stack.
A especialização só pode ser inferida quando explicitamente indicada no título ou na descrição.

TÍTULOS COM ESTÁGIO/TRAINEE — extrair o cargo subjacente:
Se o cargo subjacente for genérico demais para ser canônico válido ("TI", "Tecnologia",
"Informática", "Sistemas" sem qualificador), retornar canonical_role: "Cargo Indefinido".
- "Estagiário de Engenharia Civil" → canonical_role: "Engenheiro Civil"
- "Trainee de Dados" → canonical_role: "Analista de Dados"
- A senioridade vai para seniority_inferred

ENGENHEIRO vs. DESENVOLVEDOR:
- Título com "Engineer" em inglês → verificar foco:
  "Cloud Engineer" → "Engenheiro de Cloud" (sempre — está na lista de referência)
  Arquitetura/sistemas/infraestrutura de software → "Engenheiro de Software"
  Infraestrutura de TI/redes → aplicar regras de Infraestrutura/Redes/Suporte
  Implementação/features/produto sem especialização explícita → "Desenvolvedor"
  Backend/Frontend/Full Stack Engineer → "Desenvolvedor [especialização]"
  "Software Engineer" → sempre "Engenheiro de Software"
- "Engenheiro de Sistemas":
  Foco software/kernel/firmware → "Engenheiro de Software"
  Foco industrial/construção/física → manter "Engenheiro de Sistemas"

ACRÔNIMOS E TERMOS PROIBIDOS como canonical_role:
Nunca retornar: SDR, BDR, BDM, RH, TI, CSM, AM, AE como cargo único
Nunca retornar: Hunter, Farmer, Closer, Qualifier, Prospector
Nunca retornar: títulos internos sem equivalente de mercado

Normalizar para canônicos válidos:
SDR / Sales Development Representative → "Representante de Pré-Venda"
  (se B2B enterprise → "Executivo de Pré-Venda")
BDR / Business Development Representative → "Analista de Desenvolvimento de Negócios"
Hunter → "Executivo de Vendas" ou "Representante Comercial"
Farmer → "Gerente de Contas"
CSM / Customer Success Manager → "Gerente de Customer Success"
AM / Account Manager → "Gerente de Contas"
AE / Account Executive → "Executivo de Contas"

ORTOGRAFIA — verificar antes de retornar:
Erros comuns a evitar: "Assistante" (correto: "Assistente"), "Engenhero" (correto: "Engenheiro"),
  "Desenvovedor" ou "Desenvolvedro" (correto: "Desenvolvedor")

4d. SINGULAR E PLURAL — A LISTA DE REFERÊNCIA É A AUTORIDADE:
Use a forma exata (singular ou plural) com que o cargo aparece na Lista de Referência. A forma da Lista prevalece sobre qualquer regra geral de número.
Exemplos da Lista: "Gerente de Produto" e "Designer de Produto" (singular); "Gerente de Projetos" e "Coordenador de Projetos" (plural).
Para cargos FORA da Lista, use a forma predominante no mercado brasileiro para aquele cargo específico — não force plural nem singular de forma cega (ex: "Arquiteto", nunca "Arquitetos").

4e. TRADUZA TÍTULOS HÍBRIDOS COM PREPOSIÇÃO EM INGLÊS:
Títulos que contenham preposições em inglês como "of", "of the", "for" devem ser integralmente traduzidos — não apenas parcialmente.
Exemplos:
- "Head of AI & Automation" → "Head de IA e Automação"
- "Head of Engineering" → "Head de Engenharia"
- "Director of Operations" → "Diretor de Operações"
Termos consolidados no mercado BR que podem permanecer em inglês:
"Tech Lead", "Product Owner", "Scrum Master", "DevOps", "SRE".

4f. EVITE CANÔNICOS GENÉRICOS SEM QUALIFICADOR:
Canônicos como "Desenvolvedor", "Analista" ou "Consultor" sem qualificador só são válidos quando a descrição genuinamente não permite inferir a especialidade. Se a descrição menciona tecnologia, área ou domínio específico, use-o.
Exemplos:
- Descrição menciona frontend/React/CSS → "Desenvolvedor Frontend", não "Desenvolvedor"
- Descrição menciona dados/SQL/BI → "Analista de Dados", não "Analista"
- Descrição menciona vendas/comercial → "Consultor Comercial", não "Consultor"
Prefira sempre o canônico mais específico que a descrição suportar.

4g. PREPOSIÇÃO "DE" vs "EM":
Sempre usar "de" na construção do canonical_role:
- "Técnico em Refrigeração" → "Técnico de Refrigeração"
- "Técnico em Eletrônica" → "Técnico de Eletrônica"
Exceção: cargos na Lista de Referência que usam "em" (ex: "Especialista em SAP").

4h. ABREVIAÇÕES EM QUALIFICADORES:
Nunca usar abreviações no qualificador:
- "Coordenador de RH" → "Coordenador de Recursos Humanos"
- "Analista de BI" → "Analista de Business Intelligence"
Exceção: siglas que são o nome consolidado no mercado
(SRE, DevOps Engineer, Product Owner, UX Designer).
"Gerente de TI" está na Lista de Referência — manter.

4i. QUALIFICADOR ESPECÍFICO — NÃO remover qualificadores que diferenciam domínios:
- "de TI", "Industrial", "Tecnológica", "Patrimonial", "do Trabalho"
  são diferenciadores reais entre funções de setores distintos.
  Ex: "Analista de Infraestrutura de TI" ≠ "Analista de Infraestrutura" (pode ser civil/predial)
      "Supervisor de Manutenção Industrial" ≠ "Supervisor de Manutenção" (pode ser predial)
      "Analista de Inovação Tecnológica" ≠ "Analista de Inovação" (pode ser de processos)
Só remover qualificador quando for genuinamente redundante e não existir
ambiguidade setorial. O ajuste de número (singular/plural) segue a Lista de
Referência (regra 4d) e não conta como remoção de qualificador.

4j. SINÔNIMOS DE NÍVEL/CARGO:
- "Auxiliar" = "Assistente" → normalizar para "Assistente"
  (exceto "Auxiliar de Limpeza" que está na Lista de Referência)
- "Diretor de Finanças" → "Diretor Financeiro" (forma mais comum)
- "Procurement" → "Compras" (traduzir sempre)

─── REGRAS DE DESAMBIGUAÇÃO ───────────────────────────────────────────────────

SEGURANÇA — sempre qualificar o domínio (nunca retornar sem qualificador):
Indicadores TI/cyber/dados          → "… da Informação"
Indicadores vigilância/patrimônio   → "… Patrimonial"
Indicadores NR/EPI/saúde ocupacional → "… do Trabalho"

INFRAESTRUTURA — sempre qualificar (nunca retornar sem sufixo):
- Contexto TI/cloud/redes/servidores → "Analista de Infraestrutura de TI"
  (NUNCA apenas "Analista de Infraestrutura")
- Contexto predial/elétrica/hidráulica/mobiliário → "Analista de Facilities"
- "Infraestrutura" sem qualificador no mercado BR = predial/facilities.
  Se o contexto for tech, OBRIGATÓRIO adicionar "de TI".
Mesma lógica para Gerente:
- Gerente + infra + contexto TI → "Gerente de Infraestrutura de TI"
- Gerente + infra + contexto predial → "Gerente de Facilities"

AUTOMAÇÃO:
Título com RPA / Robotic Process Automation, ou automação de processos (UiPath, Power Automate) → "Desenvolvedor de Automação"
Título genérico + IaC (Ansible, Terraform, Kubernetes, CI/CD) → "DevOps Engineer"

MONITORAMENTO:
Diagnóstico, análise preditiva, relatórios, causa raiz → "Analista de Monitoramento"
Operação de alertas, escalonamento, runbooks, plantão NOC → "Técnico de Monitoramento"

INFRAESTRUTURA / REDES / SUPORTE — avaliar nesta ordem:
1. Título Engineer/Engenheiro + redes/network/telecom → "Engenheiro de Redes"
2. Título Analista + redes/network + foco analítico → "Analista de Redes"
3. Foco em telecom/fibra/instalação de infraestrutura → "Técnico de Telecom"
4. Foco em LAN/WAN/suporte de redes → "Técnico de Redes"
5. Foco em Data Center / rack / colocation → "Técnico de Data Center"
6. Instalação física / FTTH / CFTV / cabeamento → "Instalador Telecom"
7. Helpdesk / service desk / chamados de TI → "Analista de Suporte TI"
8. Suporte generalista sem especialização (fallback) → "Técnico de Suporte"
Regra de fallback conservador: sem evidência técnica suficiente, usar o canônico mais conservador compatível com o título.

ANALISTA DE NEGÓCIOS — desambiguação por foco:
Levantamento de requisitos, BPMN, UML, interface TI-negócio → "Analista de Negócios"
Backlog, critérios de aceite, gestão de produto → "Product Owner"
Valuation, DCF, fusões e aquisições → "Analista de M&A"
Prospecção, novos negócios, parcerias → "Analista de Desenvolvimento de Negócios"
CRM operacional, Sales Ops, RevOps → "Analista de Sales Operations"

ANALISTA DE OPERAÇÕES — desambiguação por foco:
Liquidação, conciliação, câmbio, mercado de capitais → "Analista de Operações Financeiras"
Frota, armazenagem, roteirização, WMS → "Analista de Operações Logísticas"
Cloud/infra (AWS, Kubernetes, Terraform) → aplicar regras de infraestrutura
Implantação de sistemas, onboarding de plataformas → "Analista de Implantação"
Genuinamente genérico (fallback) → "Analista de Operações"

ANALISTA DE DESENVOLVIMENTO — desambiguação por contexto:
Título com especialização: "… Mobile", "… Full Stack" → preservar especialização
Foco em código/implementação sem especialização explícita no título ou na descrição → "Desenvolvedor"
Foco em processos/requisitos/negócio → "Analista de Sistemas"
"… de Sistemas" → "Analista de Sistemas"

DESIGN:
Sem qualificador → inferir pelo contexto (UX, UI, Produto, Gráfico)
Impossível inferir → "Designer Gráfico"
Nunca retornar apenas "Designer"
"Design Lead" / "Design Manager" → "Coordenador de Design"

ENSINO vs. TREINAMENTO CORPORATIVO:
Escola/graduação/EAD/curso livre → "Professor"
Onboarding/T&D/LMS/treinamentos NR em empresa → "Instrutor de Treinamento"

COORDENADOR + TECH LEAD no mesmo título:
Nível gerencial prevalece → inferir como Coordenador pelo domínio
Ex: "Coordenador de Desenvolvimento - Tech Lead" → "Coordenador de Sistemas"

INFERÊNCIA AUTÔNOMA:
Quando o cargo não estiver na Lista de Referência nem coberto pelas regras acima,
infira diretamente pelo título + descrição. Não hesite — um canônico válido inferido
é sempre preferível a colapsar em genérico sem evidência.
Canônico válido = reconhecível no mercado BR, sem acrônimo isolado, sem título interno.

FALLBACK DE ABSTENÇÃO:
Se não houver evidência suficiente para definir um canonical_role reconhecível com segurança
(vaga truncada, descrição ausente, cargo interno sem equivalente de mercado),
retorne "Cargo Indefinido". Prefira abstenção controlada a classificação inventada.
Exceção: se o título for autoexplicativo (ex: "Gerente de Produto Sênior", "Desenvolvedor Backend"),
use-o para inferir canonical_role e seniority_inferred mesmo com descrição ausente ou muito curta.

─── REGRAS DE DESAMBIGUAÇÃO — HIERARQUIA E CARGOS BILÍNGUES ───────────────────

REGRA A — Hierarquia distinta exige canônico distinto.
Coordenador ≠ Gerente ≠ Diretor ≠ Head ≠ C-level. Nunca agrupe vagas de hierarquias
diferentes no mesmo canônico, mesmo quando a função subjacente seja idêntica.
"Chief Customer Officer" não é "Gerente de Customer Success" — é "Diretor de Customer
Success". Se o canônico do nível hierárquico identificado não existir no catálogo de
referência, sinalize canonical_role com o canônico da função no nível mais próximo
disponível, mas nunca colapse níveis hierárquicos distintos em um mesmo canônico.

REGRA B — Função primária identificada por tokens de domínio, não por posição.
Em títulos em português, a primeira palavra usualmente identifica a função principal:
"Analista de Projetos e Customer Success" é Analista de Projetos. Em títulos em inglês,
o padrão é invertido: "Customer Success Operations Manager" tem função principal
"Operations Manager" modificada pelo domínio "Customer Success" — não é Customer
Success Manager. Use os tokens do título para identificar a função primária,
considerando ambos os padrões (PT antepõe função, EN pospõe).

REGRA C — Delivery sobre pre-sales quando há ambiguidade.
"Solution Consultant", "Solutions Engineer", "Technical Consultant" em descrições que
mencionam implementação, customização, integração, onboarding ou entrega de projeto
são funções de delivery (Consultor, Engenheiro de Implantação). Quando a descrição
enfatiza venda, demonstração, discovery ou proposta comercial, são funções de pre-sales
(Consultor Pré-Vendas). Na ausência de sinal claro, assuma delivery — é o caso mais
comum no catálogo brasileiro.

REGRA D — Título IC prevalece sobre seniority hierárquico aparente.
"Senior Developer", "Lead Engineer" com responsabilidade técnica individual são
Desenvolvedor Sênior, Desenvolvedor Lead — NÃO Gerente de Engenharia. Títulos IC
(Individual Contributor) não mudam de canônico funcional por senioridade. Só migre
para canônico gerencial quando a descrição mencionar explicitamente gestão de pessoas,
orçamento, headcount, processo de contratação, avaliação de desempenho, mentoring
estruturado com cadência formal.

REGRA E — Cargos US sem equivalente BR mantêm o termo em inglês.
"Product Owner", "Scrum Master", "DevOps Engineer", "SRE", "Growth Hacker"
são termos incorporados ao mercado brasileiro
e devem ser mantidos em inglês mesmo quando o título da vaga venha em PT. Não force
tradução para "Dono de Produto", "Mestre Scrum" ou similar. Exceções naturais: "Developer"
vira "Desenvolvedor", "Engineer" vira "Engenheiro", "Analyst" vira "Analista" — o catálogo
usa termos em PT nesses casos.

Siglas C-level (CTO, CEO, COO, CMO, CFO) são canônicos em inglês, como termos
incorporados. CCO é intencionalmente rejeitado por ambiguidade tripla (Chief Customer,
Chief Commercial, Chief Content Officer) — "Chief Customer Officer" mapeia para "Diretor
de Customer Success" (ver REGRA A).

MICRO-REGRA CONTEXTUAL — SUPPORT/SERVICE BILÍNGUE

"Customer Support" ou "Customer Service" em empresa brasileira (sem outro
qualificador) → "Analista de Customer Service" ou "Analista de Customer Experience",
NUNCA "Analista de Suporte".

"Support" em inglês em contexto de clientes finais, pedidos, entregas, reservas, SAC
→ "Analista de Customer Service".

"Suporte" em português aplica-se apenas quando for a software, sistema ou produto
técnico com chamados, incidentes ou troubleshooting de TI.

PROPOSTA DE MAPEAMENTO PARA TAXONOMIA (regra binária)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Se você ESTÁ CRIANDO um canonical novo (ou seja, o canonical_role que você
retorna NÃO consta literalmente na Lista de Referência fornecida), você DEVE
incluir o campo `proposed_taxonomy_mapping` no output JSON com:

"proposed_taxonomy_mapping": {
  "source_term": "<title da vaga, lowercase + trim, REMOVENDO o qualificador de nível já capturado em seniority_inferred (Sr., Jr., Sênior, Júnior, Pleno, Especialista, Estágio, I/II/III, Senior/Junior/Staff/Principal) — manter só o cargo funcional>",
  "target_canonical_label": "<label do canônico criado, sem senioridade>",
  "confidence": <número entre 0 e 1 — sua certeza de que source_term mapeia para target_canonical_label>
}

Se o canonical_role que você retorna BATE EXATAMENTE com um canônico já
existente na Lista de Referência, OMITA o campo (não há proposta nova a fazer).

Esta regra é INDEPENDENTE da camada de resolução — vale para Camadas 0, 1, 2 e 3. O critério é: criou canonical novo → emite; usou canonical existente → omite.

FAIXAS DE CONFIDENCE (interpretadas pelo gate server-side):
- confidence ≥ 0.85 → mapeamento entra direto como ativo no catálogo (auto-promoção, sem revisão Opus)
- 0.70 ≤ confidence < 0.85 → mapeamento fica em zona de revisão (vai pra fila Opus para arbitragem)
- confidence < 0.70 → mapeamento é descartado (não entra no catálogo)
Use 0.90+ quando o source_term é claramente uma variante linguística direta do target (mesma raiz, mesmo papel).
Use 0.70-0.84 quando há ambiguidade semântica plausível (mesma área mas role pode ser distinto).
NUNCA emita o campo abaixo de 0.70 — prefira omitir todo o proposed_taxonomy_mapping.

Exemplo concreto (canonical novo "Head de Engenharia" não está na Lista):
{
  ...,
  "canonical_role": "Head de Engenharia",
  "canonical_confidence": 0.78,
  "proposed_taxonomy_mapping": {
    "source_term": "head of engineering",
    "target_canonical_label": "Head de Engenharia",
    "confidence": 0.95
  }
}

PROPOSTA DE ALIAS PARA SKILL
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Quando, em uma skill emitida, você reconhecer que o `name` que está usando é
uma VARIANTE de um canonical skill já estabelecido (acrônimo, abreviação,
tradução, plural, erro tolerável, variante comum), inclua o campo
opcional `proposed_alias` DENTRO do objeto da skill com:

"proposed_alias": {
  "raw": "<variante original como apareceu na vaga, lowercase + trim>",
  "category": "<UMA das 11 categorias abaixo>",
  "confidence": <número entre 0 e 1 — sua certeza de que raw é variante do canonical skill>
}

CATEGORIAS (use a mais específica aplicável — preferir granular sobre genérica):
- "acronym"               — sigla (ex: "PM" → "Project Management")
- "abbreviation"          — abreviação não-sigla (ex: "JS" → "JavaScript")
- "translation"           — tradução PT-EN / EN-PT (ex: "developer" → "desenvolvedor")
- "plural_inflection"     — variação plural (ex: "APIs" → "API")
- "misspelling_tolerable" — erro tolerável (ex: "javascrit" → "JavaScript")
- "common_variant"        — variante comum (ex: "Reactjs" → "React")
- "synonym"               — sinônimo direto (ex: "frontend" → "front-end")
- "domain_alias"          — variante de domínio (ex: "ML" → "Machine Learning" em data)
- "specialty"             — especialização específica
- "slang"                 — gíria do mercado
- "other"                 — não cabe nas anteriores (use ÚLTIMO)

VALORES INVÁLIDOS (não inventar — mapeie ou rejeite):
- "noun_inflection"/"singular_inflection"/"singular" → use "plural_inflection" (cobre variação morfológica em ambos os sentidos)
- "technical"/"technical_term"/"technical_jargon" → NÃO é categoria linguística; é o tipo da skill. Use "specialty" se for termo especializado do domínio, ou "other" como último recurso
- "related"/"related_concept"/"related_activity" → REJEITE o alias. Conceitos correlatos não são equivalências semânticas — não emita proposed_alias
- "expansion" → use "abbreviation" (a forma extensa de uma sigla cabe no par sigla↔extenso)

Se nenhuma das 11 acima couber após este mapeamento, prefira OMITIR proposed_alias a inventar categoria nova.

FAIXAS DE CONFIDENCE: idênticas às do gate definidas acima em proposed_taxonomy_mapping (≥0.85 → ativo direto; 0.70 ≤ confidence < 0.85 → fila Opus; <0.70 → descartado).
Use 0.90+ para variantes morfológicas óbvias da mesma raiz (plural, acentuação, casing).
Use 0.70-0.84 quando há ambiguidade semântica plausível (acrônimos ambíguos, traduções com múltiplas leituras).
NUNCA emita o campo abaixo de 0.70 — prefira omitir todo o proposed_alias.

Omita o campo se o name emitido já bate exatamente com canonical existente
ou se você não reconhece variante. NUNCA emita proposed_alias para skills
genéricas ("Excel", "Inglês") onde a variação é ortográfica trivial.

Exemplo:
{
  "name": "javascript",
  "type": "technical",
  "confidence": 0.9,
  "proposed_alias": { "raw": "javascrit", "category": "misspelling_tolerable", "confidence": 0.92 }
}
